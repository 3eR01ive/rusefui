# Knock-спектрограмма: перенос FFT с ECU в rusefui

Размышления о том, как снять тяжёлый FFT-расчёт с MCU и считать спектрограмму на стороне rusefui (Rust), сохранив при этом возможность непрерывной записи 10–15 секунд.

## Как сейчас сделано на ECU

### Сэмплирование

`firmware/controllers/sensors/impl/software_knock.cpp`:

- ADC3 в DMA, частота: на F4 `STM32_PCLK2 / (4*(84+12)) ≈ 218.75 kHz`, на H7 — той же величины (см. `firmware/config/boards/proteus/knock_config.h`). 12 бит.
- На каждое искрообразование (`Engine::onSparkFireKnockSense` → `scheduleByAngle` → `onStartKnockSampling`) запускается **разовый** `adcStartConversionI` в `sampleBuffer[1800]`. Длина окна = `oneDegreeUs * knockSamplingDuration / 1e6` (примерно 1–4 мс на цилиндр), т.е. это **не непрерывный поток**, а короткие выстрелы по событию.
- По завершении DMA — `BinarySemaphore`, поток `KnockThread` идёт считать RMS (`processLastKnockEvent`).

### FFT и спектрограмма

`firmware/controllers/sensors/impl/fft/fft.hpp` — самописная радикс-2 Cooley–Tukey над `std::complex<float>`, плюс окна Hann/Hamming/Blackman/Blackman-Harris.

В `software_knock.cpp`:

```cpp
struct SpectrogramData {
    fft::complex_type fftBuffer[FFT_SIZE];
    float window[FFT_SIZE];
};
```

При `FFT_SIZE=1024`: `complex<float>[1024] = 8 КБ` + `float window[1024] = 4 КБ` ⇒ **12 КБ постоянно в `.bss`**. Плюс `sampleBuffer[1800]` (3.6 КБ), но он нужен и для обычного RMS-детектора, его не убрать.

Считается **по одному столбцу за искрообразование**: блэкман-харрис → `ffti` (in-place, 1024 точки) → `amplitude` 64 бинов начиная от ~4 кГц → `toDb` в `uint8_t` → пакуется в 16 `uint32_t` → `m_knockSpectrum[16]`.

### Транспорт на хост

`firmware/controllers/engine_cycle/knock_controller.txt`:

```
uint32_t[16 iterate] m_knockSpectrum;Knock: SpectrumData;"compressed data",1, 0, 0, 0, 0
uint16_t m_knockSpectrumChannelCyl;Knock: ChannelAndCylNumber;"compressed N + N", 1, 0, 0, 0, 0
uint16_t m_knockFrequencyStart;Knock: Start Freq;"Hz", 1, 0, 0, 0, 0
float    m_knockFrequencyStep;Knock: Step Freq;"Hz", 1, 0, 0, 0, 0
```

Это — поля **обычного output-channels блока** (`TS_TOTAL_OUTPUT_SIZE = 2044`), который TunerStudio/rusefui дёргают командой `O`. То есть 64 байта сжатой спектрограммы + 8 байт метаданных едут вместе с остальной телеметрией.

Java-плагин (`KnockAnalyzerTab.java`) подписывается на 16 имён `m_knockSpectrum1..16`, складывает индексы, и когда чек-сумма индексов сошлась — рисует столбец канваса.

## Где здесь память и почему "лог медленный"

**Память:** дорогая часть — именно **12 КБ FFT-буфера + окна**. FFT идёт *на каждый цилиндр*, окно держится постоянно как кеш. Это и хочется убрать с MCU.

**"Лог медленный":** под "логом" имеется в виду путь `O` → `output_channels.rs`. В `rusefui-runtime`:

```rust
const OUTPUT_POLL_HZ: f64 = 200.0;
const POLL_INTERVAL: Duration = Duration::from_nanos((1_000_000_000.0 / OUTPUT_POLL_HZ) as u64);
```

200 Гц × 2044 байта ≈ 410 КБ/с теоретического потолка, и весь блок шарится со всеми гейджами/CSV-логом. Чтобы прокачать спектрограмму **по сырым отсчётам** через `O`, надо было бы класть туда 218 000 байт/с — это убьёт всю остальную телеметрию. Поэтому путь "через лог" — тупик, и не из-за USB, а из-за того, что `O` это **опрос фиксированного блока структуры**, а не поток.

## Что у rusefi уже есть для "сырых" больших дампов

Существует ровно нужный паттерн — **trigger scope** (`firmware/console/binary/trigger_scope.cpp`):

- Перевод ADC в **8-битный DMA-режим** (`ADCD3.dmamode &= ~MSIZE_MASK; |= MSIZE_BYTE`) — bandwidth × 0.5.
- Заполняет `BigBuffer` (`BIG_BUFFER_SIZE = 8192`).
- Когда DMA завершён — `engine->outputChannels.triggerScopeReady = true` (бит в обычном output-блоке).
- Хост видит флажок, шлёт `TS_SET_LOGGER_SWITCH` + `TS_TRIGGER_SCOPE_READ`, MCU отдаёт **весь буфер одним CRC-кадром** через `tsChannel->sendResponse(TS_CRC, buffer, size, true)`.
- Через 10 мс перезапускает сэмплирование.
- Mutually exclusive с `enableSoftwareKnock` — делят ADC3.

Тот же скелет уже подтверждённо работает на боевых железяках (alphax-2/4/8chan). Для нашей задачи он почти готовый.

## Бюджет байт/секунд

Native knock-ADC поток: 218 750 отсчётов/с.

| Вариант | Bandwidth | 10 с данных | Памяти на MCU |
|---|---|---|---|
| 8-битный raw, 1 канал | **218 КБ/с** ≈ 1.75 Мбит/с | 2.2 МБ | 8 КБ DMA-буфер |
| 8-битный raw, 2 канала | 437 КБ/с | 4.4 МБ | 8 КБ |
| 8-бит + decimation ×4 (АА-фильтр в DMA half-cb) | 54 КБ/с | 540 КБ | 8 КБ |
| 12-бит сырой (как сейчас sampleBuffer) | 437 КБ/с | 4.4 МБ | 8 КБ |

USB-CDC FS у rusefi тащит ~700–900 КБ/с на bulk (это уже отработано на tooth logger). 218 КБ/с проходит **с большим запасом**.

Никакого "буферизировать 10 с на MCU" не нужно — у F4 столько RAM просто нет. Это должен быть **поток**, а не дамп.

## Архитектура

### На стороне ECU

Сделать **"knock scope"** — клон `trigger_scope.cpp`, но:

1. Использует **уже существующий `KNOCK_ADC`** и `KNOCK_PIN_CH1/2`, никакой новой пиновой обвязки.
2. ADC в DMA-режиме, **double-buffer** (half-transfer + complete колбэки ChibiOS — у `trigger_scope` они не задействованы, поэтому он не "потоковый", а "выстрел–пауза"). Это ключевое отличие: пока хост вытягивает буфер A, MCU уже льёт в буфер B. Без этого будут дыры 10–20 мс на каждую перезарядку, и непрерывной записи 10–15 с не получится.
3. Команда хоста — **новый sub-code к существующему `TS_SET_LOGGER_SWITCH`** (`TS_KNOCK_SCOPE_ENABLE/READ/DISABLE`), по той же схеме, что `TS_COMPOSITE_*` и `TS_TRIGGER_SCOPE_*`. Никакого нового опкода, никаких ломок INI-протокола.
4. Признак готовности — новый бит/счётчик в обычном output-блоке (`m_knockScopeReady` + `m_knockScopeSeq`), чтобы поллинг `O` на 200 Гц видел, "какую половину забирать".
5. **`SpectrogramData[12 КБ]` выпиливается** в этом режиме (`#ifdef KNOCK_SPECTROGRAM_ON_HOST`). Окно и FFT-буфер уходят на хост. Сам по себе knock-RMS (`m_knockLevel`, `m_knockCyl`) можно сохранить — он считается по тем же байтам в half-callback на лету (sum-of-squares за окно), это десятки тактов, не нагрузка.
6. Mutually exclusive — как `trigger_scope` уже сделан: либо обычный per-spark `software_knock`, либо knock-scope. Переключается флагом в конфиге.

Итого на MCU: **минус 12 КБ `.bss`, минус O(N log N) FFT за каждое искрообразование**. Прибавляется один DMA-callback (несколько десятков строк) и пара полей в output channels.

### На стороне rusefui (Rust)

В `crates/rusefui-runtime/src/sources/` появляется `knock_scope.rs` рядом с `composite_data_log.rs`:

- Свой `thread::Builder` (по образцу `output_channels.rs`), который:
  1. шлёт `TS_KNOCK_SCOPE_ENABLE` через `session.try_with_link(...)`;
  2. подписывается на `m_knockScopeSeq` из `OutputSnapshot.values` (он уже декодируется в общем поллере) — это его триггер;
  3. на изменение `seq` шлёт `TS_KNOCK_SCOPE_READ`, получает 8 КБ;
  4. кладёт байты в `crossbeam_channel::Sender<Vec<u8>>` или прямо в `RingBuffer<f32>` (`heapless::spsc` / `ringbuf` крейт, ёмкость ~512 КБ = ~2.5 с запаса под джиттер UI-потока).
- Отдельный `FftWorker` (тоже поток):
  - тянет из ринга окна по 1024 отсчёта со страйдом 256 (75% overlap),
  - `rustfft::FftPlanner::plan_fft_forward(1024)` + предвычисленный Blackman-Harris,
  - `|X|^2 → dB`, сохраняет в `Vec<Vec<u8>>` (столбец на окно) с временной меткой.
- Состояние в `Arc<RwLock<KnockScopeState>>`, наружу — `serde_json::Value` через привычный `ComponentLogic::state()` (как у `dyno.rs`).

Никаких математических операций тяжелее FFT 1024 на десктопном CPU — это микросекунды в `rustfft`. 218 кГц / 256 ≈ 854 столбца спектрограммы в секунду; даже наивная реализация съест < 1% ядра.

### Frontend (Vue)

Новый `src/components/builtins/KnockSpectrogram.vue` рядом с `OutputChart.vue`/`Dyno.vue`. Получает от runtime массив колонок (u8 или f32 нормированные) + start_freq/step/timestamps, рисует heatmap на `<canvas>` через `putImageData` (или WebGL, если будут тормоза — для 854 колонок/с и высоты 64 px он не нужен, обычный 2D хватает).

## Ответы на ключевые подвопросы

**"Через лог" — почему медленно и можно ли исправить.**
Лог = опрос `O`. Он по архитектуре не может тащить 218 КБ/с raw, потому что блок фиксированного размера и шарится со всем остальным. Чинить смысла нет — у rusefi уже есть выделенный механизм (`TS_SET_LOGGER_SWITCH`/big-buffer/CRC-response), и именно его надо переиспользовать. Это **тот же физический USB**, но другая логическая команда без полльного потолка.

**Хватит ли пропускной способности на 10–15 с непрерывной записи.**
Да, с большим запасом: 218 КБ/с при 8 бит / 437 КБ/с при 12 бит, 1 канал. USB-CDC у rusefi уверенно отдаёт ~800 КБ/с (tooth logger тому пример). **Узкое место — не USB, а пере-арм DMA.** Текущий `trigger_scope` имеет 10 мс паузу между буферами — это даст ~25% потерянных отсчётов. Решение — **half-transfer DMA в режиме circular**, тогда непрерывность гарантирована.

**Что физически делать с FFT-памятью на ECU.**
В режиме knock-scope-on-host структура `SpectrogramData` (12 КБ) не аллоцируется вообще — спрятать под отдельный `#ifdef`/`engineConfiguration->knockSpectrogramHost`. Это и есть прямая экономия, ради которой всё затевается. `sampleBuffer[1800]` остаётся (он же нужен для RMS), но можно даже его не использовать в этом режиме, потому что DMA пишет в `BigBuffer`.

**Нужно ли вообще хранить 10–15 с на хосте.**
Нет смысла держать `Vec<u8>` на 2.2 МБ. Архитектура streaming-first: входной ring ~512 КБ, FFT-worker сразу превращает байты в столбцы спектрограммы (1 столбец = 64–128 байт), 10 с спектрограммы = 854 столб/с × 10 × ~128 байт ≈ 1 МБ — нормально. Если нужна "плёнка для прокрутки назад" — это уже отдельный круговой буфер столбцов, не raw-отсчётов.

**Возможные неприятности.**
- Half-transfer DMA + USB-bulk-send — это две очереди, между ними нужен thread-safe drain (typical pattern: DMA пишет в SRAM, USB-thread читает `ready` флаг и шлёт; если хост зевнул и буфер перетёрся — увеличить счётчик "overrun" и идти дальше).
- Mutex с обычным `software_knock` — не давать включать оба одновременно (как уже сделано с `trigger_scope`).

## Резюме (первая итерация)

1. **Не растягивать `O`.** Это поллинг фиксированного блока, его потолок ~200 Гц независимо от железа.
2. **Скопировать паттерн `trigger_scope`** для knock-ADC, с добавлением half-transfer DMA (= потоковость без дыр). USB-CDC справится.
3. **FFT целиком переезжает в `rusefui-runtime`** (`rustfft`/`realfft`), там же декомпрессия в столбцы спектрограммы, Vue только рисует. Освобождается ровно те **12 КБ** `.bss` на MCU (`SpectrogramData`), плюс снимается O(N log N) с каждой искры.
4. **Continuous 10–15 с** обеспечивается на стороне MCU только при double-buffered DMA. На хосте достаточно ~512 КБ ring + FFT-worker — это «копейки» для десктопа.
5. **Сырые ADC-байты ходят через тот же USB, что и live-data**, но через отдельный логический канал (`TS_SET_LOGGER_SWITCH` + новый sub-code) — никакого пересмотра INI/протокола.

## Уточнение по разрядности ADC: 8 бит или 12 бит?

В первой версии плана я по инерции списал паттерн с `trigger_scope` (8 бит). Это неверно по умолчанию — у `trigger_scope` 8 бит сделаны под конкретную задачу (форма триггерного меандра — где 8 бит избыточны). Для knock-спектрограммы аргументы наоборот в пользу 12 бит.

### Bandwidth — посмотрим ещё раз

- 12 бит, 1 канал: 218 750 × 2 байта = **437 КБ/с ≈ 3.5 Мбит/с**
- 8 бит, 1 канал: 218 750 × 1 байт = **218 КБ/с ≈ 1.75 Мбит/с**

USB-CDC FS у STM32 теоретически 12 Мбит/с, практически ~6–8 Мбит/с на bulk-out. **437 КБ/с — это меньше половины** реалистичного USB-bulk. Tooth logger в rusefi прокачивает сравнимые объёмы и не давится. Так что "в 2 раза меньше байт" — да, приятно, но **бутылочное горлышко нигде**, и экономить нечего.

### Что упрощается с 12 бит на MCU

Сейчас в `software_knock.cpp` ADC работает именно в 12 бит:

```cpp
static NO_CACHE adcsample_t sampleBuffer[1800];
```

`adcsample_t` — это halfword (uint16_t), DMA нативно настроен на 12-bit/16-bit memory. То есть **ничего специального для 12 бит писать не надо — это default ChibiOS-ADC**. Это `trigger_scope` делает странный спецтрюк:

```cpp
ADCD3.dmamode &= ~(STM32_DMA_CR_PSIZE_MASK | STM32_DMA_CR_MSIZE_MASK);
ADCD3.dmamode |= STM32_DMA_CR_PSIZE_BYTE | STM32_DMA_CR_MSIZE_BYTE;
```

Каждый раз, когда ADC3 переключается между "обычным" knock (12-bit, halfword DMA) и trigger-scope (8-bit, byte DMA), эти регистры надо корректно перенастраивать. В нашем случае — если оставить 12 бит, **просто не трогаем регистры, никакого риска что-то не восстановить**.

### Качество сигнала

- 12 бит — нативные ~72 дБ динамики. FFT-бины при возведении в квадрат складывают шум, и noise floor спектрограммы ограничен именно ENOB ADC. На 8 бит floor поднимется примерно на 24 дБ.
- На H7 есть `H7_KNOCK_OVERSAMPLE 4` — `firmware/config/boards/proteus/knock_config.h`. Hardware oversampling × 4 добавляет ENOB. Понижать после этого до 8 бит — терять то, что специально добавили.
- Сейчас существующий код `processLastKnockEvent` пересчитывает в напряжения через `ratio = 3.3f / 4095.0f` — это и есть 12-бит ratio. Если мы хотим **параллельно с raw-стримом** на лету считать RMS в half-transfer DMA-колбэке (чтобы `m_knockLevel`/`m_knockCyl` продолжали работать как сейчас), удобнее иметь те же 12 бит и тот же ratio — без отдельной 8-bit ветки.

### Что упрощается на rusefui-стороне

В Rust FFT-воркер всё равно конвертирует в `f32`:
- u16→f32: одна инструкция, один масштаб (× 3.3/4095).
- u8→f32: то же самое, ровно одна инструкция. Никакой разницы.

То есть на хосте 12 vs 8 бит — это **0 строк кода и 0 нс перфоманса**.

### Где 8 бит реально имеет смысл

1. **Не-USB транспорт** — Bluetooth-serial (~50 КБ/с практически), CAN-gateway. Там 218 КБ/с уже не пролезает.
2. **Если хочется два канала одновременно** (CH1+CH2) — тогда 437×2 = 874 КБ/с в 12 бит уже на грани USB-bulk; в 8 бит = 437 КБ/с, спокойно.
3. **Если хочется на MCU всё-таки оставить копию буфера** в SRAM для какого-нибудь параллельного анализа — память пополам.

То есть 8 бит — это не "лучше по умолчанию", а опция для конкретных bandwidth-критичных конфигураций.

### Решение по разрядности

- **Default — 12 бит, halfword DMA**, ничего не переключаем. Соответствует тому, как `software_knock` уже работает с ADC3.
- Опционально (через `engineConfiguration`-флажок типа `knockScopePacking`) можно добавить **8-бит режим только для double-channel** (CH1+CH2 синхронно) или для медленных транспортов. Но это второй приоритет, не для первой итерации.
- **Никакого packed-12-bit** (3 байта на 2 отсчёта) — экономит 25% за счёт ~30 строк pack/unpack кода и риска рассинхрона. Не стоит свеч.

Итого: **12 бит правильнее по умолчанию**, и одновременно это ещё и меньше кода на MCU, потому что не надо лезть в `dmamode`-регистры.
